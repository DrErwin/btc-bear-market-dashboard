# GitHub README 的 GEO 改写原则研究

研究日期：2026-07-30  
适用对象：`BTC 熊底证据看板` GitHub README  
研究范围：只讨论如何让 README 更容易被人和生成式搜索系统理解、引用与核对，不讨论工程结构。

## 结论先行

对这个项目最有效的 GEO 做法，不是堆砌 “BTC、熊底、链上指标” 等关键词，而是把 README 写成一份**清楚、可信、可直接引用的产品说明**：

1. 开头两三句话明确回答“它是什么、解决什么问题、不能做什么”。
2. 使用稳定一致的中英文产品名，并给出唯一的正式看板链接。
3. 用普通人会问的问题组织内容，例如“如何判断 BTC 是否接近熊底？”。
4. 写出项目独有的方法：两条状态轴、人工回测阈值、16 项指标、受约束的 AI 解读、数据质量处理。
5. 对关键事实给出数字、固定状态名称、来源或可核对入口，不写无法证明的宣传语。
6. 明确作者、方法、用途和安全边界。该项目涉及金融市场，可信度比关键词密度更重要。
7. 保留简短英文摘要，但不要为了覆盖搜索词机械复制整篇内容。

这些做法可以提高内容被正确理解和引用的机会，但**不能保证任何搜索排名、AI 引用或流量结果**。

## 适用于本项目的具体改写原则

### 1. 先建立明确的“产品实体”

README 首屏应固定使用：

- 中文名：BTC 熊底证据看板
- 英文名：BTC Bear-Bottom Evidence Dashboard
- 类型：公开、只读的比特币链上周期研究工具
- 核心问题：当前市场压力有多深；熊市筑底过程走到了哪里
- 正式入口：公开看板链接
- 限制：不预测精确最低点，不提供交易建议

这样能减少 AI 把它误解为交易信号、价格预测器或普通链上数据站的风险。Bing 官方也建议让文字、图片和其他格式对同一实体保持一致。

### 2. 把项目独有的方法写成可引用事实

值得保留并说清楚的原创事实包括：

- 使用两条彼此独立的状态轴，而不是一个“见底／未见底”结论。
- 压力轴有 5 个固定状态；筑底过程轴有 7 个固定状态。
- 使用 16 项周期指标，分成估值与成本、供应盈亏、链上资本流、持有者行为、矿工压力和长期成本锚等证据组。
- 指标阈值来自项目作者对历史熊市的人工回看和校准。
- AI 负责在固定事实和边界内解释证据，不修改阈值，也不输出交易动作。
- 缺失、过期和仅供展示的数据不会作为当前状态证据。

这些内容同时满足“独特、具体、可核查”三个要求，比重复泛泛的“专业 BTC 分析平台”更有价值。

### 3. 用普通人的问题作标题，用第一句话直接回答

建议使用真实阅读问题，例如：

- 什么是 BTC 熊底证据看板？
- 它如何判断 BTC 熊市处于什么阶段？
- 为什么需要压力轴和筑底过程轴？
- 看板包含哪些 BTC 链上指标？
- AI 在看板中做什么，又不能做什么？
- 它能找到 BTC 的最低点吗？

每节第一句先给短答案，再补充解释。Bing 官方明确提到清楚标题、表格和 FAQ 有助于内容被准确引用；Google 同时提醒，不要为了覆盖查询变体制造大量重复内容。因此，一个紧凑、真实有用的 FAQ 足够。

### 4. 补齐“谁、如何、为什么”

Google 对可信内容的自查建议包括：

- **谁做的**：明确作者或维护者，并链接到真实身份入口。
- **如何做的**：说明人工阈值、数据检查和受约束 AI 分析之间的分工。
- **为什么做**：帮助普通用户理解熊底是一个过程，而不是制造抄底信号。

对于涉及投资和财务稳定的话题，Google 表示其系统会更重视能够体现信任的信号。因此，本项目应保留研究用途、数据限制和非投资建议声明，并避免“精准抓底”“成功率”等未经验证的表述。

### 5. 让数字和来源真正支持内容

可安全使用的具体数字包括“16 项指标”“2 条状态轴”“压力轴 5 个状态”“筑底过程轴 7 个状态”。这些数字来自产品本身，容易核对。

指标来源应连接到看板中的具体说明或可信的一手来源。不要为了符合论文中“统计与引用可能提高可见性”的发现，加入与产品无关的数字或引用。引用的作用是让读者核对事实，不是装饰。

### 6. 保持中文主体，提供紧凑英文摘要

项目支持中英文界面，因此保留稳定的英文产品名和一段完整英文摘要是合理的。英文摘要应覆盖：

- 产品是什么；
- 两条状态轴回答什么；
- 使用哪些类型的链上指标；
- AI 的边界；
- 不提供交易建议。

不需要逐段复制整篇中文，也不需要把每个关键词的英文变体全部塞进去。Google 官方表示其系统能够理解同义词和一般语义。

## 不建议做的事

1. **不要堆关键词**：反复重复 BTC bear bottom、Bitcoin bottom indicator、crypto bottom 等词会降低可读性，Google 也将关键词堆砌列为不应采用的做法。
2. **不要为 AI 写空泛宣传语**：例如“最准确”“行业领先”“精准抄底”，除非有公开可核验的比较证据。
3. **不要承诺排名或引用结果**：Google 明确表示，即使满足要求，也不保证抓取、收录或展示；Bing 的引用次数也不代表排名或权威性。
4. **不要把论文中的最高实验提升写成产品承诺**：GEO 论文的“最高 40%”来自特定基准和系统，且论文明确指出不同领域效果不同。
5. **不要为了搜索新建大量相似问答**：Google 最新指南明确反对为查询变体批量制造内容。
6. **不要把 `llms.txt` 当成 Google GEO 必需项**：Google 明确说它不使用此文件来决定生成式 AI 搜索可见性。
7. **不要隐藏 AI 的作用和边界**：应明确 AI 做的是有约束的证据解释，不是事实生成器或自动交易顾问。
8. **不要让中英文描述互相矛盾**：两种语言中的指标数量、状态含义、产品边界和正式名称应一致。

## 针对现有 README 的建议结构

1. 标题与一句话定义
2. 正式看板入口与研究用途警示
3. “快速了解”事实表：产品类型、分析对象、两条状态轴、指标数量、更新方式、语言和边界
4. “它如何判断 BTC 熊市阶段？”：解释双轴方法
5. “为什么不是寻找某一刻的熊底？”：说明熊底是过程
6. 核心功能
7. 指标与六类证据
8. AI 做什么／不能做什么
9. 如何阅读看板
10. 作者与项目目的
11. 常见问题
12. English summary

这个结构是内容建议，不要求每一项都独立成很长的章节。README 应保持紧凑，避免因为 GEO 反而牺牲普通人的阅读体验。

## 证据边界与发布后的验证

- 学术论文提供的是实验性规律；Google、Bing 和 OpenAI 的官方文档才是各自产品当前可公开确认的规则。
- GitHub 页面是否允许某个爬虫访问由 GitHub 平台控制。项目作者可以优化 README 内容，但不能仅通过 README 保证 OAI-SearchBot、Googlebot 或 Bingbot 一定抓取。此处是根据 OpenAI 和 Google 爬取文档作出的平台控制推论。
- 发布后可观察 GitHub/看板访问、搜索收录和可获得的 AI 引用数据，但不能只凭一次 AI 回答判断 GEO 成功。
- 内容变化应是真实产品变化，不应只改日期制造“新鲜感”。
